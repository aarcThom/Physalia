Standalone web chat window driving the GH pipeline, **additive** to the classic Prompter (both offered; classic keeps its canvas panel + Image Sources `/<alias>` input). Plugs into the [[signal-lifecycle]]. **Authoritative plan doc:** `planning/chat-window.md` in the repo.

## Shape
A `Chat` GH component (no inputs, one `Prompt Signal` output) owns a standalone Eto `WebView` window. Sending mints a Prompt Signal exactly like Prompter; the window reads the wired Conversation Log's conversation / live stream / busy state by **wire-graph traversal** (no inputs, so connecting a wire never re-solves) and pushes them to the page. Why small: Prompter was already signal-source + traversal-UI; the window reuses the traversal.

**Host = Eto.Forms `WebView`** (one class, WebView2 on Windows / WKWebView on Mac, uniform custom-URI bridge) — chosen for Mac-ease. Verified Windows engine = Chromium/WebView2 (`Edg/149`), so Svelte renders fine.

## The UI: `src/Physalia.UI` (new project in `src/Physalia.slnx`)
Vite + Svelte 5 + TS + Tailwind v4 + **shadcn-svelte** with **svelte-ai-elements** registry components (conversation, message, response, chain-of-thought, tool, prompt-input, image + shadcn bases), in `src/lib/components/{ui,ai-elements}`.
- **MSBuild wrapper** (compiles no C#): the Vite build runs only with `-p:BuildUI=true` or `npm run build` — a plain `dotnet build` needs no Node and uses the committed artifact.
- **Output (changed 2026-06-29):** `vite-plugin-singlefile` → one `src/Physalia.UI/dist/index.html` → **embedded into the `Physalia.GH` assembly** as the `Physalia.GH.chat.html` manifest resource (via `Physalia.GH.csproj`'s `EmbedChatHtml` target). It is NOT in `Files/` (that folder is user-alterable content only). At runtime `ChatWindow.TryExtractChatHtml` writes it to `%TEMP%/Physalia/chat-<asmVersion>.html` (reused when present + same size) and `LoadUi` loads that via `file://`. singlefile = no module fetches, so `file://` works AND avoids the WebView2 `NavigateToString` ~2 MB limit (the bundle is too big for `LoadHtml`).
- **Bundle 16 MB → ~3.4 MB:** streamdown-svelte (the Response markdown renderer) drags in Shiki-all-langs + mermaid(+cytoscape) + katex; singlefile inlines them all. `vite.config.ts` regex-aliases unused Shiki grammars (keep `json`), non-github themes, and `mermaid`/`katex` → empty stubs (`src/lib/shiki-empty-lang.ts` = `[]`; `src/lib/empty-module.ts` = noop Proxy). Safe — the chat enables no math/diagram plugins so those imports are never reached. `code/shiki.ts` trimmed to json+text, 2 themes.
- **Nothing streamdown ships is styled by our build** — Tailwind scans `src/`, never `node_modules`, so the
  package's own class strings (its `shadcn` theme AND its link-safety modal) are simply absent from the
  bundle — which is what made its external-link dialog render as unreadable text over the
  conversation. **Fixed 2026-09-05**: `@source '../node_modules/streamdown-svelte/dist';` in
  `app.css` compiles the package's classes (+27 kB), and `response.svelte` passes a `theme` override
  re-scaling the result for a 460px panel. See [[chat-link-prompt]].
- **Light mode forced:** NO `ModeWatcher` mounted, `.dark` never applied, `app.css` `color-scheme: light` (so response.svelte's `mode.current` → undefined → light theme).

## Required features (all implemented)
- **Thinking → ChainOfThought, tool calls → Tool.** Core conversation has NO reasoning channel, so `<think>…</think>` is parsed out of assistant text in the UI (`splitThinking` in `bridge.ts`) → ChainOfThought; the rest → Response. Tool calls are surfaced from `ToolCallContent` + the matching `ToolResultContent` (both in `MessageContent.cs`) → Tool component (state input-available / output-available / output-error). NB `ai-elements/tool/` has NO index.ts — import the `.svelte` files directly.
- **Images (reworked 2026-06-21):** the ai-elements `PromptInput` attachment intake was DEAD in the `file://` WebView — every path (picker/paste/drop) funnels into `AttachmentsContext.add()` which calls `crypto.randomUUID()` (throws, not a secure context) + `URL.createObjectURL` BEFORE storing, so the file was silently dropped (symptom: "Add image" opens the picker and nothing else happens). `Composer.svelte` was rewritten to do its own WebView-safe intake: `FileReader.readAsDataURL` → base64 (no blob URLs), counter ids (no `crypto.randomUUID`), plain DOM `paste`/`dragover`+`drop` (document-level, = old globalDrop)/hidden `<input type=file>`. Each add inserts a Claude-Code-style `[image#N]` token at the caret + a thumbnail in a strip above the textarea (× to remove → drops the token & renumbers). Tokens are composer-only: **stripped from the text before send** (regex `/\[image#\d+\]/g`); images travel as real `SubmitImage` blocks. Downstream UNCHANGED & already-correct: `App.svelte` `send()` (stash `__physaliaPending` + `phbridge://submit?images=1`), `ChatWindow.HandleSubmit`/`BuildMessages` (base64 ↔ `InlineImage`), conversation `<Image>` render. Builds + svelte-check clean; live Rhino test pending.
- **JSON auto-collapse:** LLM ghjson dumps flooded the chat. `bridge.ts` `splitContent(text)` splits an assistant body into prose vs JSON — catches ```json fences, unlabelled fences whose body parses as JSON, large bare JSON in prose (≥120 chars), and a large *unclosed* bare-JSON tail (collapses mid-stream). `AssistantTurn` renders prose via `Response`, each JSON segment via `chat/JsonBlock.svelte` (shadcn Collapsible, closed by default; the Code view + CopyButton mounts only when expanded, to skip Shiki cost). Non-JSON fences stay in prose.

## Bridge contract (`src/Physalia.UI/src/lib/bridge.ts` ↔ `Panels/ChatWindow.cs`)
- **C# → JS** via `ExecuteScriptAsync` on a 0.15 s `UITimer` (change-detected): `window.physalia.{setHistory(UiMessage[]), setStream(text|null), setState({connected,busy,ready,needsSetup,status})}`. (`ready` is pushed but the JS ignores it; `needsSetup` drives the setup screen — see below.)
- **JS → C#** via custom-URI navigation the host cancels:
  - text-only: rides the URL query `phbridge://submit?text=<enc>` (the proven path; `ChatWindow.GetQueryValue` parses it).
  - with images: sets `?images=1` and stashes the full JSON on `window.__physaliaPending` (base64 too big for a URL); host pulls it back via `__physaliaTake()` (with a one-layer JSON-unwrap in `ParseSubmitMessage`, since Eto may return the result JSON-encoded). **The pull MUST use `await _webView.ExecuteScriptAsync(...)`, NOT synchronous `ExecuteScript` — the sync variant on Eto/WebView2 pumps-and-waits and unreliably returns null, which silently dropped EVERY image send (text-only worked because it rides the URL). `HandleSubmit` is `async void` for this. Fix landed 2026-06-21 (.gha rebuilt), awaiting live confirmation; do not revert to sync ExecuteScript.**
- C# side: `OnDocumentLoading` sets `e.Cancel=true` synchronously, then **defers** the work via `Application.Instance.AsyncInvoke` (running a GH solve / ExecuteScript inside the nav callback re-enters the WebView core and crashes Rhino — same hazard as `ManageImagesDialog`'s grid-edit deferral). → `Chat.SubmitFromWindow(text, contentBlocks?)`.

## First-run setup state (landed 2026-06-21, builds clean)
Shown when **no LLM provider is configured at all** — distinct from the pipeline-wiring `ready` flag. Takes precedence over every other state (nothing to chat with until a provider exists).
- **Detection (C#):** `Panels/ProviderAvailability.AnyConfiguredAsync(apiKeyConfigPath, HttpClient, ct)` returns true if ANY of: an API key resolves from `API_KEY_CONFIG.YAML`/env (`Api.GetKeys(...).Count>0`), the Claude Code CLI is on PATH (`ClaudeCodeProvider.IsCliAvailable()` — new public method; delegates to `ClaudeCodeSession.IsCliAvailable()` → refactored `TryResolveExecutable(out path)`, a PATH-presence check, NOT auth), or a local llama-server answers `LlamaCppServerQuery.GetPropsAsync(new LlamaCppConfig(), ...)` at the default `http://127.0.0.1:8080/v1`. Cheap checks short-circuit before the network probe (the llama endpoint is only hit when nothing else is set up). "Claude detected" = **CLI installed on PATH** (user's explicit choice), not a running process.
- **Cadence:** `ChatWindow.MaybeProbeProviders()` runs the probe off the UI thread via `Task.Run` (3 s `CancellationTokenSource`; shared static `ProbeClient` with a 2 s `HttpClient.Timeout`), result published back on the UI thread (`Application.Instance.AsyncInvoke`). Cached in `bool? _providersConfigured` (null until first probe — assume configured so the setup screen never flashes), re-probed every 4 s so it clears within seconds of adding a key / starting a server. `Tick` reads the cache: `needsSetup = _providersConfigured == false`; when set, `status = "Setup mode"`.
- **UI:** `src/lib/chat/Setup.svelte` replaces the conversation surface when `showSetup` (in `App.svelte`, `{#if showSetup}<Setup/>{:else}…{/if}` inside `ConversationContent`). Placeholder red-smiley SVG (swap for real art later) + welcome + provider grid.

Then resets `_providersConfigured=null` to force re-probe (key resolves on the next tick → setup clears), and pushes `window.physalia.setSetupResult({provider,ok,message})` (new host→JS verb; one-shot, not via Tick) which `Setup` shows as a green/red banner. **Key never logged.** NB the config file lives next to the assembly (bin/Files at dev time) so a `dotnet build` `RemoveDir` wipes it — same as the existing ApiKeys component; an installed `.gha` persists it.

## Gotchas
- **Home survives losing the Chat that backs it (2026-08-17).** Home is a window STATE (`_home`), but `_component` still points at whichever Chat was last viewed — and `OnComponentRemoved` used to `SetActiveComponent(next)` on that removal, which clears `_home` and drops the user into some other harness's conversation. It now re-backs `_component` and stays on Home. Reachable any time a viewed Chat is deleted; the harness "Load from .gh file" action hits it every time. Companion seams added the same day: `Chat.ActiveWindow` (reach the one open window WITHOUT opening one) and `ChatWindow.IsViewing(chat)` — sample the latter BEFORE tearing a Chat down, since afterwards the window has already re-pointed itself somewhere arbitrary.
- **Static surfaces must live OUTSIDE `<Conversation>` (2026-08-09).** Home / the empty-harness logo, the setup screens and the header pages (preset, grounding, manual definition) render in their own scroller — a sibling `div` under the same `relative min-h-0 flex-1 pr-3` wrapper, classed to mirror `ConversationContent`'s own (`flex flex-col gap-8 p-4` + `chat-scroll overflow-y-scroll`), picked by `staticSurface = showSetup || panel !== null || showConnect`. Inside the Conversation they open **scrolled past their own logo**: `stick-to-bottom-context.svelte.ts`'s MutationObserver jumps to the bottom on any content change while `isAtBottom && !userHasScrolled`, and a freshly swapped-in surface satisfies both. Do NOT try to fix that by assigning `scrollTop = 0` — the observer reacts on a `requestAnimationFrame` and would undo it a frame later, and its `isAtBottom` test carries a **200 px threshold**, so a panel that overflows by less than that reads as "at bottom" even when pinned to the top. A separate element sidesteps all of it: a freshly mounted scroller starts at the top, and switching back remounts the Conversation, which correctly jumps to the latest message.
- **Nothing may be pushed before `DocumentLoaded` — push-once state is lost forever otherwise (fixed 2026-08-09).** `_loaded` is set *before* `LoadUi()` and the timer starts immediately, so `Tick` began pushing while the ~3.4 MB bundle was still extracting and parsing. `Exec` is fire-and-forget and every pushed script is guarded by `window.physalia&&…`, so those pushes vanish silently — and `window.physalia` is installed in `onMount`, long after. History/state/stream survive it (change detection re-pushes on the next change), but the two **global** signatures do not: `_lastPresetSignature` latches on that swallowed first tick and the `Files/PRESETS` set never changes, so the preset gallery stayed EMPTY for the life of the window. Reopening "fixed" it only because that builds a fresh `ChatWindow` *and* the temp bundle is already extracted, so the load wins the race. `_lastChats` (switcher row) had the same shape. Fix: `_pageReady`, latched by the first `DocumentLoaded`, gates `Tick`; `MarkPageReady` clears every cache **including** `_lastPresetSignature`/`_lastChats`. **Latch it — on WebView2 a cancelled `phbridge://` nav also raises `DocumentLoaded`** (`NavigationCompleted`, `IsSuccess=false`), so an unlatched reset would force a full history re-push on every user action. A ~5 s tick backstop assumes ready if the event never fires, so a backend that doesn't raise it degrades to the old race rather than a dead window. **Any future push-once state must be cleared in `MarkPageReady`.**
- **The UI bundle is EMBEDDED in `Physalia.GH`, not in `Files/` (changed 2026-06-29):** `Files/` is reserved for user-alterable content, so the compiled chat UI must not live there. `src/Physalia.UI/dist/index.html` (the singlefile bundle, ~3.3 MB, gitignored via `src/Physalia.UI/.gitignore`) is embedded as the `Physalia.GH.chat.html` manifest resource by `Physalia.GH.csproj`'s `EmbedChatHtml` target. A fresh clone must build it (`dotnet build src/Physalia.slnx -c Debug`, which runs Vite) or the window shows "UI not found". Verify: built `.gha` is ~3.9 MB and `GetManifestResourceNames()` includes `Physalia.GH.chat.html`.
- **`EmbedChatHtml` hook + ProjectReference plumbing:** `Physalia.GH.csproj` takes a build-ordering `ProjectReference` on `Physalia.UI` (`ReferenceOutputAssembly=false SkipGetTargetFrameworkProperties=true UndefineProperties="TargetFramework"` — the last two are REQUIRED, else GH's net7.0-windows TFM flows to the net7.0 UI wrapper and restore fails NETSDK1005). `EmbedChatHtml` hooks `BeforeTargets="SplitResourcesByCulture"` (NOT `CoreCompile` — too late, resource prep is a CoreCompile dependency) with the `Exists(dist/index.html)` check on the TARGET (deferred until after the UI builds; a static `<EmbeddedResource Condition="Exists()">` evaluates pre-UI-build and embeds nothing). `BuildUI` defaults **true** in `Physalia.UI.csproj`; the Vite target is incremental (`Inputs`=`src/**`+root config globs, `Outputs`=`dist/index.html`). `-p:BuildUI=false` → dist absent → not embedded → "UI not found" page.
- **Per-config staleness:** the embedded resource lives in the `.gha` for the config you actually build, so iterating Debug leaves the **Release** `.gha` frozen at its last build. Build the SAME config Rhino loads (or build both).
- **UI-only change still recompiles GH (verified 2026-06-29):** `dist/index.html` is a `CoreCompile` input (via `@(EmbeddedResource)`), so touching it makes `dotnet build` re-embed it into the `.gha`; CoreCompile stays incremental otherwise. **VS caveat:** editing only a `.svelte` file may leave GH "up to date" so VS's fast-up-to-date-check skips it — that's why BOTH `Physalia.UI.csproj` AND `Physalia.GH.csproj` carry `<DisableFastUpToDateCheck>true</…>`; still do Build/Rebuild if the UI looks stale. **Runtime loads the extracted temp copy, so a C# change needs a Rhino restart; a UI-only change needs a rebuild + reopen the window.**
- **create-vite v9:** scaffold with exactly `--template svelte-ts --no-interactive --overwrite`; extra/unknown flags silently fall back to vanilla-ts.
- **shadcn-svelte add:** `use-clipboard` hook isn't shipped by the registry (had to hand-write `src/lib/hooks/use-clipboard.svelte.ts`); `code.svelte` `@reference`d the SvelteKit demo's `routes/layout.css` (repointed to `../../../../app.css`).

## Built-in "/export" command (2026-07-08, builds clean, live test pending)
Typing exactly `/export` in the prompt box (alone; embedded in a longer message it's ordinary text) saves the viewed conversation as a `.txt` transcript for debugging — every turn verbatim (assistant `<think>` reasoning and raw JSON/Python replies included), each tool call with input JSON + output/error, images as size-stamped placeholders.

No new bridge verb — it rides the existing `phbridge://submit?text=` path.
- Composer: `BUILTIN_COMMANDS = ['export']` always appended to `availableKinds()` (no grounding/tool needed), shown in the `/` menu with a Download icon as "Export conversation (.txt)"; accepting inserts `/export ` (complete command — no sub-path, no menu reopen, unlike `/c//cl//t/`).
