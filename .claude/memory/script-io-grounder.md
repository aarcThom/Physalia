# Script I/O grounder (built 2026-07-31 as "Interface Lock", renamed 2026-08-11; not yet run live in Rhino)

Grounding-section component that freezes a script component's I/O so LLM pushes can't break existing wires. **The old name "Interface Lock" is gone** — display name AND nickname are now `Script I/O`, class/file `ScriptIO` (`Components/Grounding/ScriptIO.cs`), attrib `ScriptIOAttrib`, gradient `ArrowStyles.ScriptIO`, transmitter-side accessor `ScriptTransmitterBase.ActiveScriptIO`. **ComponentGuid pinned** (`B7D2F4A9-…0A46`), per the [[component-rename-plainspoken]] precedent, so saved `.gh` files round-trip. Behaviour words ("locked interface", `RespectsLockedInterface`, the grounding's "LOCKED interface" prose) were deliberately KEPT — locking is still what it does; only the component's name changed. Read the rest of this file with the old name mentally substituted.

**Shape:** `InterfaceLock : PhyBase` (`Components/Grounding/InterfaceLock.cs`, GUID `B7D2F4A9-…0A46`) — no inputs, one `Param_Grounding` output, grip-links to a **PyTransmitter** (not the script component) via `InterfaceLockAttrib : GripLinkAttrib` with new `ArrowStyles.InterfaceLock` gradient (LimeGreen→Teal), anchor top-centre−6 of the transmitter. Link persisted as `LinkedGuid`. SolutionEnd signature watch (ToolsInUse pattern) re-solves when the target's interface changes.

**Core:** `ScriptInterfaceGrounding(ComponentName, Inputs, Outputs)` + `ScriptInterfacePort(Name, TypeHint, Access-string)` in `Grounding.cs`; renders the locked contract as verbatim-copyable `"inputs": [...]/"outputs": [...]` JSON entries (type omitted when untyped — schema allows that). Stable (not volatile). Falls through the ConversationLog `default` arm — **no chat-UI pill/panel was added** (no per-kind selection UI; add later if wanted).

**Enforcement (PyTransmitter):** `FindInterfaceLock()` scans the doc for an `InterfaceLock` where `Constrains(InstanceGuid)` (linked + not GH-disabled — disabling the lock suspends enforcement without unlinking). Under lock, `PushSolve` does `SetScript` + `Expire` ONLY — skips SetInputs/SetOutputs/SetOutputsNoTypeHint/EnableOutputMarshalling and leaves `_inputs/_outputs` empty so the access re-apply pass never runs. Validation: declared input/output names must be a **subset** of the target's live names (fewer is fine — params are never rebuilt; unknown = add/rename → reject). Violation → `_lockFeedback` routed as Fail (Warning level) containing the grounding's own contract rendering (reuse via `InterfaceLock.ToPorts` + `ScriptInterfaceGrounding.ToSystemPromptSection`), code NOT pushed.

**Type-hint read-back** (new, was impossible in repo before): `GhPythonBridge.GetInputSpecs/GetOutputSpecs` return `GhParamSpec`s; hint recovered via `IScriptParameter.Converter?.TargetType?.Type` (compile-time accessible — `IParamValueConverter.TargetType` is a `Rhino.Runtime.Code.ParamType` with `.Type`) reverse-mapped through `TypeHintMap`; null converter / unmappable / throw → empty (untyped). Outputs always empty hint by design.

**Why:** [[dead-wire-lint-projected-graph]] and friends guard the graph the LLM produces; this guards a HUMAN-owned component the LLM merely scripts. Related: [[human-tools-taxonomy-moves-2026-07]] (grounding taxonomy), [[python-output-list-access]] (why the push path mutates access at all).

**SUPERSEDED IN PART, 2026-08-11 — the lock is no longer Python-only.** See [[csharp-transmitter]]. What changed: `IsValidTarget` / `TryResolveTargetScript` widened `PyTransmitter` → `ScriptTransmitterBase`; `FindInterfaceLock`/`ValidateAgainstLockedInterface`/`BuildLockFeedback` moved OFF PyTransmitter onto that base as `ActiveScriptIO`/`RespectsLockedInterface`; `ScriptInterfaceGrounding` gained a required 4th param, `ScriptInterfaceDialect` (Core — `ComponentKind`/`SchemaName`/`CodeRule`, `.Python` and `.CSharp`), read off `ScriptTransmitterBase.Dialect` so no language branch lives in the lock. The **subset** rule above is now Python-specific: `AllowsPartialInterface` is false for C#, where the RunScript signature restates the interface and an omitted param has nothing to bind to.

**Stale-contract bug found + fixed 2026-08-11: the signature watch was on the WRONG DOCUMENT.** `AddedToDocument` subscribed `document.SolutionEnd` — the harness SUB-document — but the target script component lives on the HOST canvas, so a user editing its params (adding an input, renaming a variable, re-hinting) solves the HOST and never the harness. This component has no inputs, so nothing else ever expires it: it kept serving the interface as it stood when the transmitter was first linked. **One subscription was correct before the harness split and silently wrong after it — worth checking any other component that watches `SolutionEnd` from inside a harness.**

Fix: watch BOTH. Local covers the LINK changing (the transmitter is a harness peer, so re-pointing it re-solves locally); host covers the INTERFACE changing. `WatchHost()` re-points on every solve AND every callback rather than being set once, because the harness owner is often unresolvable at `AddedToDocument` time (dropped into a harness still being placed, or a file load) — set-once would leave the watch permanently off. With no harness, host == local and the host watch is deliberately skipped so callbacks don't double-fire. The signature needed nothing: `SpecKey` = `Name:TypeHint:Access` joined in order, plus nickname and InstanceGuid, so add/remove/rename/re-access/re-hint/reorder all register.

**Second half of the same bug, found in live Rhino testing: a RENAME reaches no SolutionEnd at all.** After the host watch landed, input changes refreshed but output renames still did not. Root cause is GH's expiry graph, and it is worth remembering generally: **a param's recipients are DOWNSTREAM of it.** Renaming an INPUT expires that param → its recipient is the COMPONENT → component expires → solution runs → any SolutionEnd watch catches it. Renaming an OUTPUT expires that param → its recipients are whatever is wired below it → **the component sits UPSTREAM of its own output and is never touched**, so an *unwired* output rename expires nothing and runs no solution anywhere. No solution watch of any kind can see it. That asymmetry is the whole explanation for "inputs work, outputs don't".

Fix: a THIRD watch — `IGH_DocumentObject.ObjectChanged` on the target component AND on each of its params, filtered to `GH_ObjectEventType.NickName`/`NickNameAccepted` (`GH_Document` has no document-level ObjectChanged, so it must be per-object). Re-synced alongside `WatchHost` on every solve and callback, since the param set changes; add/remove DOES expire the component, so a solution brings us back to pick up the new list. Both name events are kept rather than just `NickNameAccepted` — missing a rename is the bug being fixed — so a solve may be scheduled per keystroke while renaming; the signature compare makes each one a no-op and GH coalesces the schedule.

**Third round, 2026-08-12 — the rename watch DIED at the first push.** Symptom: an output rename registered before the first prompt but never after the LLM had responded. The user's theory was that the system prompt is fixed for the conversation; **it is not** — `ConversationLog.SolveInstance` calls `ReadGroundingInputs` every solve and the latch composes `new Instructions(BuildGroundedSystemPrompt(...), ...)` fresh at mint time, with no caching in either. Verified; nothing on the ConversationLog side needed changing. **When a grounding looks stale mid-conversation, suspect the grounder, not the log.**

Real cause: a transmitter push calls `UpdateInputParameters`/`UpdateOutputParameters`, which **REPLACE the parameter objects** rather than mutating them (and `SetScript` alone can re-derive them via auto-declare). Every `ObjectChanged` handler from the previous round was then attached to a discarded param, and the fresh params carried none — so the watch worked exactly until the first push and silently never again. Fix: handle `GH_ObjectEventType.Layout` on the target COMPONENT (which survives a param rebuild, making it the one safe anchor) by re-running `WatchTarget()` before the refresh check. **Any long-lived subscription to a script component's params has this bug shape — re-arm off the component, never assume the param objects persist.**

**Two things were tried in that same pass and REGRESSED it — neither rename was detected any more. Do not re-try either:**
- **`ExpireSolution(true)` in the scheduled callback.** Reasoning was that a collapsing schedule flushed early leaves a bare mark with nothing to pick it up. But GH flushes scheduled delegates at the START of the next solution, so `ExpireSolution(FALSE)` is exactly right — the solution now beginning collects the component. Passing `true` asks for another solution from inside that one, which is re-entrant and killed the refresh outright. **`false` is load-bearing here.**
- **Treating `Layout` as a contract-change trigger.** Layout fires WHILE the parameter set is mid-rebuild, so it samples a half-built interface into `_lastSignature`; every later comparison is then made against garbage. Layout may re-arm the subscription (`WatchTarget()`) and nothing more — it must not call `RefreshIfContractChanged`.

General lesson from this one: the working mechanism was replaced on a theory rather than added to. When a live-tested path works in one case and not another, keep the working path byte-for-byte and add beside it.

**ACTUAL ROOT CAUSE, 2026-08-14 — the scheduled solve was dropped because the harness sub-document was not solving.** Found by exporting a real conversation and reading it, after two theory-driven fixes missed. The transcript settled it in one glance: the rejection feedback (which reads the target LIVE at push time) correctly listed the user's newly added `foundation` output, while the same turn's system prompt clearly did not — the model invented `a` for its third output, which it would never do if it had been told. So the READ was always right, the TRIGGER was always right (`checked — contract unchanged` proved the event fired and `_lastSignature` had caught up), and the only broken link was the re-solve in between.

Why: the change happens on the USER'S CANVAS, so the host solves and the harness does not. A harness sub-document is only re-enabled when its proxy solves (`HarnessComponent.ReviveInner`), and **a disabled document ignores scheduled solutions outright** — the csproj comment on `ReviveInner` says so in as many words. So `ScheduleSolution` posted onto the sub-document from a host-side event is dropped on the floor, the expire never runs, and the stale contract is served to the next inference.

Fix: **mark expired, do not schedule.** `ExpireSolution(false)` directly (falling back to a schedule only when the local document is genuinely mid-`Process`). Nothing needs to recompute at that instant — it needs to be recomputed before the NEXT inference, and this component is upstream of the Conversation Log, so the solve the user's next prompt causes re-solves it first and puts fresh grounding on the wire before the latch reads it. **Any harness-resident component reacting to a host-side event has this bug shape: do not post work to the sub-document's scheduler, just expire and let the next pipeline solve carry it.**

Two diagnostics were added and are worth keeping: a canvas caption showing the contract last emitted (`2 in / 3 out`, or `unlinked`), and a right-click **Trace Interface Watch** (session-only, off by default) that logs each watch/check decision to the Rhino command line. The caption is what makes "did this component even see the change" answerable at a glance instead of inferred from model behaviour.

ENFORCEMENT was never stale — `RespectsLockedInterface` reads the live specs off the target at push time. Only the GROUNDING (a cached output) went stale. Still open: after a user edits a locked C# component's params, the code already pushed no longer matches the signature and the target errors until the model resubmits — the refreshed grounding makes the NEXT submission right, but nothing forces one.
