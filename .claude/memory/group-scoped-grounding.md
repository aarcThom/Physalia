Built 2026-07-28 on `feat/group-based-context` because LLMs get confused by pre-existing canvas nodes. Builds clean, 339 Core tests green. **Run live in Rhino the same day** (White House staged build, chat + trace triaged): enrollment, scoped export/grounding, id preservation, and the full 5-stage loop all worked — the model finished in prose with correct massing. But the first cut's checksum frame prefix cost 2 wasted rounds per stage:

**HARD LESSON — a frame marker cannot live inside the checksum string.** The first cut minted scoped checksums as `sha256-group-<hex>`. Physalia's own schema passed it, but the GhJSON LIBRARY's ghpatch schema (reference-only NuGet, validated by GH Definition Validator) regex-rejects any non-`sha256-<hex>` shape — and its error flattening then co-reported bogus "All values fail against the false schema" errors on perfectly valid internalizedData entries (branch-knockout noise, same family as the 2026-07-25 `not`-branch bug). The model coped by STRIPPING `group-`, which silently dropped every patch into the full frame; every one of the 5 stages burned the same 3-round dance (regex reject → strip prefix → mismatch → full-frame checksum → apply). **Fix: both frames use plain `sha256-…` and the frame is resolved by MATCHING** — `GhJsonBridge.ResolveBaseSnapshot(doc, carried)` tries the active frame's export first, then the other frame; used by `ApplyPatchToCanvas` AND `LintPatch`. Neither matches → real drift, mismatch feedback in the active frame. Identical content across frames → identical checksum → choice immaterial.

**Other session notes:** stage-1 full placement logged `id claims verified: 20/24` on a FRESH canvas with the scoped grounder — new data point for [[component-id-robustness]] (ledger pre-pass restored the authored numbering, so no harm downstream). A user-doc Fidelity Check had its Definition input miswired (payload starting with '#'); the component's own remedy message handled it — no code change. `claude_code_incremental.ghjson` preset now wires **Physalia Group Components** instead of Canvas State.

**Master group is PER HARNESS since 2026-08-17: `"Physalia <8 hex of the harness InstanceGuid>"`.** Before that a document had one group named "Physalia" and two harnesses with the scoped grounding locked onto the SAME group — each exporting the other's work as its own canvas. Chose the harness's own guid over a stored ordinal ("Physalia 1"): no new persisted field, and a COPIED harness gets a fresh guid, so it correctly reads as a new pipeline needing its own group instead of fighting the original for one (an ordinal would have to de-dup on paste). Cost is an uglier canvas label. `IsMasterGroup` matches the stem with OR without an id (any pipeline's group is infrastructure — excluded from exports/layout/id-claims); the id-SHAPE check is what keeps a user's own "Physalia tower" group in the model's view. `FindMasterGroup(doc, harness)` = exact name, else a LEGACY un-suffixed group (so older files keep grounding on what is in them); `EnsureMasterGroup` CLAIMS a legacy group by stamping the id on — on a write, never on a read, so every pipeline still reads it until one actually places. Identity threads through as `HarnessComponent?` via the new `PhyDocuments.Harness(obj)`: `TryExportCanvasState`, `MasterGroupScope`, `EnrollPlaced`, `TryCreateMasterGroupWithHint`, `CurrentBaseChecksum`, `ResolveBaseSnapshot`, `RecordActiveFrame`/`ActiveFrameIsGroupScoped` (frame registry re-keyed from document to HARNESS), plus the four bridge entry points `LoadAndPlaceJson` / `ApplyPatchToCanvas` / `LintRequiredInputsJson` / `VerifyPlacementFidelity` (params deliberately NOT optional, so the compiler finds every site). `MasterGroupFollower` now pairs each harness with its own group (`PairAnchors` keyed by harness id). Model-facing prose says "your Physalia group" — it never sees the group object, so the name is not its business.

**Master group** (`Generation/GhJsonBridge.GroupScope.cs`):
- Identity = a `GH_Group` whose NickName is `GhJsonBridge.MasterGroupName(harness)`; the NAME is the contract (rename detaches, naming your own group exactly that adopts it). Faint teal, created at the first LLM placement (bounds are its members', so it materializes at the transmitter tip) or at the transmitter's drag-out.
- `EnrollPlaced(doc, placedComponents, modelGroups?)` runs on BOTH LLM paths — `LoadAndPlaceJson` (infers model groups = groups whose members ⊆ placed set) and `ApplyPatchToCanvas` (gets created-group guids from `ApplyGroupOps`, which now returns them). Model sub-groups are enrolled as whole members; uncovered components directly. Already-covered objects are never touched.
- The master group is INFRASTRUCTURE, excluded everywhere: both export frames (`TryExportCanvasState` skips `IsMasterGroup`), `Layout.cs` area enumeration (else the whole placement fuses into one rigid body), and `RegisterPlacedGroupIds` live candidates (else a single-group placement could set-match it and steal the claim).

**2026-08-17 — the group is opened by the DRAG, not only by the first placement.** `ComponentTransmitter.HandleDrop` now calls `GhJsonBridge.TryCreateMasterGroupWithHint(hostDoc, dropPoint)` when a wired, enabled `PhysaliaGroupGrounder` sits in the SAME harness (`UsesGroupScopedGrounding`, read live off the local document — harness-scoped, since another harness is another line of work). Rationale: in the scoped frame the group IS the model's whole view, so before it exists the view is empty and the user has nowhere to opt components in. The group needs ≥1 member to have bounds at all, so it is created holding a **light robin egg blue panel (ARGB 255,168,226,219)** reading "you can add your own components to the Physalia group", sitting just ABOVE the drop point so placements land on clear canvas. The panel is identified by NickName `HintPanelName` ("Physalia") and excluded from both export frames via `IsHintPanel` — same infrastructure contract as the group, so the model never reads a note addressed to the user. Idempotent by "group already exists → do nothing", which also means a hint panel the user deletes stays deleted. Builds clean; NOT yet run in Rhino.

**2026-08-17 — the harness proxy TRAVELS with the group (`Harness/MasterGroupFollower.cs`).** Dragging the master group carries the harness proxy, its outlet wires, and the placement point with it — the point needs no work, it is stored as an offset from the proxy pivot. Membership was rejected as the mechanism (the user asked for it explicitly): group members are what the scoped grounding EXPORTS and what the model may target with a group op, so the pipeline must stay outside while reading as attached. **GH gives you nothing to hook here:** `GH_Document` raises added/deleted/solution events but **never a moved event**, `GH_ObjectEventType` has no Pivot member, and a group is moved by moving its MEMBERS (its bounds are just their union). `GH_Canvas` does expose `DocumentObjectMouseDown` + a public `GH_DragInteraction.AddAttribute(IGH_Attributes)` — the native way to make an extra object ride a drag, worth revisiting for live/undo-correct following — but neither the event's coverage of GROUP hits nor whether `GH_Canvas` re-raises WinForms MouseDown/Up could be verified without Rhino, so the shipped mechanism is a **throttled (80 ms) `RhinoApp.Idle` poll**: snapshot member pivots (nested groups expanded, group objects themselves skipped since their pivot is derived), and treat it as the group moving only when every member still present moved by the SAME non-zero delta (±0.5). One member moving alone → mixed deltas → ignored; a placement landing adds members without moving any → ignored. A proxy whose `Attributes.Selected` is true is SKIPPED — GH is already dragging the whole selection and following would double the delta (this is the select-all-and-drag guard). Watch is armed/released by `ComponentTransmitter.AddedToDocument`/`RemovedFromDocument` keyed on InstanceGuid (arming at the drop would miss a reopened file, which has group + placement point but no gesture).

**Same day, made SYMMETRIC — dragging the proxy drags the group.** `CarryGroup` translates the members (the only way a group moves; the master and any nested group get `ExpireCaches` + `ExpireLayout` so the boxes close back around them), driven by `DraggedProxyDelta`. **The load-bearing fix, and it bit on the first cut: a pass that carried something MUST re-measure before storing its anchors.** With anchors left as measured before the carry, the side just moved looks like a fresh user drag on the next pass, the opposite direction answers it, and the pair accelerates off the canvas — `Selected` does not save you, since the loop closes the moment the user deselects. Each direction also skips anything that already travelled the same delta (`AlreadyMoved`) as well as anything Selected. Nice consequence of reacting to POSITIONS rather than records: undo needs no handling at all — GH restores the side the user dragged, that restore is itself a rigid move, and the next pass carries the other side back.

**Poll interval 80 ms → 16 ms (one 60Hz frame) after the user reported it felt sluggish.** What had made a fine interval look too expensive was `GH_Document.FindObject` per group member per pass — that walks the object list, so it was quadratic in canvas size. One `Measure` sweep now indexes every object by id, expands group membership against the index (BFS, no FindObject at all), and collects member pivots + proxy pivots + the group objects needing `ExpireLayout` in the same pass. Cost per pass is one sweep of the document; the interval is a ceiling on the poll rate, not a timer. Builds clean; NOT yet run in Rhino.
