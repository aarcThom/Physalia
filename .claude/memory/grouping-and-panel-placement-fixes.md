Triage of `chat.txt` (White House session, 2026-07-25). Three user-reported symptoms, all traced to code/schema defects — none were model flakiness.

**1. The model could not group components — two unsatisfiable deadlocks.**
- Full documents: `Files/SYSTEM_PROMPTS/SCHEMA/Node Graph.json` `fullDocument` had `additionalProperties:false` over only schema/components/connections, and a rule saying "Omit document metadata and groups". No group could ever appear.
- Patches: Physalia's `groups.add` allowed ONLY name/color/members (`additionalProperties:false` → `id` forbidden), while the GhJSON library's `groupAdd` = `allOf[ghjson#groupData, not{required:[instanceGuid]}]` and `groupData.anyOf` requires `(instanceGuid+members)` OR `(id+members)` → with instanceGuid banned, `id` is MANDATORY. Literally no document satisfied both validators.
- **Library bug amplifying it:** `PatchValidator.FlattenDetails` (ghjson-dotnet) suppresses failing `anyOf`/`oneOf` branches but NOT failing subschemas under `not`. So a *correct* add (no instanceGuid) makes the inner `required` fail — which is what makes the `not` pass — and that inner failure is emitted verbatim as `Required properties ["instanceGuid"] are not present`. Comply by adding one, and `ValidateNoInstanceGuidInAdds` says "must not specify instanceGuid". Unwinnable.
- **Fixes:** shared `group` def in Physalia's schema requiring `id`+`members` and forbidding `instanceGuid`; `groups` added to `fullDocument`; new schema rules + preamble guidance on grouping; `DescribePatchError` in `GhJsonBridge.Validity.cs` strips `instanceGuid` from required-property lists reported against `*/add/*` paths and drops the error when nothing else was missing. Verified with jsonschema: library-compliant form now VALID, id-less form INVALID, instanceGuid still INVALID, full-doc groups VALID.
- `ApplyGroupOps` already handled `groups.add` correctly all along (reads name/color/members, ignores id) — only validation blocked it. It now also claims authored group ids in the stable-id registry.

**2. Panels landed in a block off to the right.** `AnchorPatchAdds` discards authored pivots by design (the preamble tells the model not to position anything) and anchors all adds as one block right of the graph, laid out from their *internal wires*. Documentation panels have zero wires → nothing to lay out, whole block dumped past the right edge. **Fix (design choice: group membership is the association):** `ExtractGroupAnchoredAnnotations` pulls unwired adds that a patch group makes a member of out of the wired block and pivots them above that group's LIVE member bounds; `LiftGroupAnnotationsAboveLayout` does the full-document equivalent (band above the layout, X-aligned with the group's leftmost wired member). Also fixed the schema rule that contradicted the preamble by telling the model to read existing pivots.

**3. Patch errors — three separate causes.**
- The instanceGuid/group deadlock above (~3 wasted rounds).
- Dangling endpoints 186/187 → partial apply: `LintPatchAdds` passed `endpointIdsMustResolve:false`, so patch endpoint ids were NEVER cross-checked against the canvas. Now it reads the canvas ids via `TryExportCanvasState` and resolves against adds ∪ canvas (`authoredIds` → `resolvableIds`, new `existingIds` param).
- False "receives 2 wires but consumes ONE item": the model emitted the SAME connection twice (`50→46[B]`); `LintRequiredInputs` counted raw connections with no dedup. GH treats a repeat as a no-op. Now deduped via `ConnectionIdentity` before counting. The bad advice had pushed the model into inventing a `Multiplication ×2` node.

**Follow-up the same day — authored pivots are now HONOURED.** The user asked for the prompt to make the model group by major functionality, annotate each group with a Panel, and deliberately plan positioning with space between functional areas. The third part was inert as written, because `RelayoutLlmGraph` discarded every authored pivot. Decision (user's, offered as a choice): **honour authored pivots as the real relative layout, keep the hierarchical relayout as a safety net only.**
- `IsAuthoredLayoutUsable` gates it: no pivots, all pivots on one point, or >30% of components involved in a pivot collision (|dx|<45 && |dy|<16 — deliberately tighter than a ~90x24 capsule, since a pivot sits at mid-left) → fall back to `HierarchicalLayout`. Otherwise keep the authored arrangement and only `FillMissingAuthoredPivots` for components with none. Verified against the transcript's real layouts: White House full doc 0/51 colliding → kept, flag patch 0/14 → kept, all-on-origin and a 10px stagger → fall back, two strays in a good grid → kept.
- `LiftGroupAnnotationsAboveLayout` now runs ONLY after a fallback relayout (which dumps unwired panels in the source column). When the authored layout is kept, the model's own panel placement stands. The patch path still overrides annotation pivots via live group bounds — in patch mode the model cannot know canvas coordinates and is told not to read them.
- Prompt: grouping-by-major-functionality + per-group explanatory Panels are now **standing, unprompted practice** (was "when asked to document"); the "spend NO reasoning on canvas placement" block is replaced with real layout guidance (150/stage X, 80 parallel Y, **200+ gutter between functional areas**, panel ~120 above its area, wires read forward, never share a pivot). Both output forms say the same thing: author in your own frame from near 0,0, the block is translated for you, never read existing pivots.

**Second live run (2026-07-25 23:03, chat.txt + signal_trace.txt) — the group-anchoring fix was INCOMPLETE.** Symptoms: group boxes stacked on top of each other, and upstream components sitting far RIGHT of the components they feed. Root cause: `AnchorPatchAdds` anchored patch adds to the right of the whole graph regardless of the group they were JOINING. My first pass only covered `groups.add` (new groups) and only UNWIRED adds. The real case was wired adds joining an EXISTING group via `groups.modify.members.add`.
- Evidence chain: round 1's full doc authored three areas side by side (Main Block x 0-360, Portico 600-1680, Wings 2000-2820) and the pivot-honouring change KEPT it — which is why the Wings group was the only tidy one in the screenshot: it never received patch adds. Round 2 added ids 46/47/48 into group 43 (Main Block) and round 3 added 49/50/51/52 into group 44 (Portico); both landed past the Wings group at the far right, so both boxes stretched across the whole canvas and all three overlapped.
- Fix: `ExtractGroupHomedAdds` (replaces `ExtractGroupAnchoredAnnotations`) handles both group sources and both kinds of add — unwired ones stack ABOVE the group as captions, wired ones become their own island placed in a row BELOW it via `PlaceWiredRowBelowGroup`, left-aligned and stepped down (max 12 × 60) until clear of live components in that column. `BuildGroupHomes` resolves the live anchor bounds from `groups.add` members and from `groups.modify` match → base group's current members. Simulated against the real session: OLD → Main Block 3460 wide, all three boxes overlapping; NEW → widths 490/1210/950, no overlaps.
- **Also fixed: the `connection_not_found` stall.** Removing a wire that is already absent was reported as a FAILED operation, and the feedback says "resubmit only the corrected operations" — but there is no correction to make, so the same remove came back forever (3 rounds in this session, on a wire an earlier rewire had already removed). Now a no-op, symmetric with the add path which already treated an existing wire as satisfied. `WireConnection`, `removing` branch.
- Confirmed working from this run: the duplicate-wire dedup did NOT suppress a genuine 2-source complaint (Construct Point 16 X coordinate really did receive Negative 14 and Series 15), and authored pivots really are being honoured.
- Still open from this run: `id claims verified: 0/39` on placement — the canvas already held the user's Button/Relay components, which claimed ids first, so authored ids 8/16/21/32/36 came back as 12/20/25/37/41. Model adapted via canvas state, but see [[component-id-robustness]]. Also the model emitted TWO JSON documents in one response (round 4, "Wait, I need to check…" then a second patch); JsonExtractor took the last, so it worked, but the preamble forbids it.

**Third live run (23:19) — layout now good except one stray.** Four groups, panels captioning each, no overlap: the honoured full-document pivots are working. The single far-right stray was a round-4 ghpatch adding `Deconstruct Domain` id 56 with **no group operation at all** — `ExtractGroupHomedAdds` found no home, so it fell through to the general right-of-everything anchor.
- Fix: `AddWireInferredHomes` — an add the model grouped nowhere is homed by following its new wires: if they reach existing components sitting in exactly ONE base group, that group is its home. Ambiguous (several groups), ungrouped-only, or add-only wiring falls through to the general anchor as before. Simulated on the real patch: id 56's wires reach 17 (Portico group) and 19 (ungrouped, so not evidence) → one distinct group → homed to Portico.
- Prompt: added "EVERY component belongs to exactly one group — no strays" to both preamble and schema, including the ghpatch form (new group's members, or `groups.modify.members.add`). This run had ids 19 and 20 in no group at all, which is also what left the wire inference with only one usable endpoint.

**Both of those then fixed (2026-07-25, same evening).**
- **"No geometry-producing components found" was a scope hole, not a scope bug in the scan itself.** `GeometryReport` (and `RuntimeHealthCheck`) accumulate watched GUIDs *only from consumed signal payloads*, and the Geometry Report sits downstream of the Runtime Health Check's **Success** output — so a turn whose graph was unhealthy never delivers its GUIDs, and they are never recovered. In that session the 48-component placement failed the health check, so the only GUIDs ever accumulated were the next patch's delta: two number-producing components → "no geometry". Fix: both guardrails now fold `GhJsonBridge.ModelPlacedGuids(doc)` (the authored-placement ledger) into the watch list at scan time, which records everything the model placed regardless of which guardrails ran.
- **The zero-geometry message also invited the wrong answer.** The report header offers "reply in prose if it matches your intent", which a model will take — ending the loop on a definition that renders nothing (and in that session it justified doing so by citing an earlier geometry report that never existed). The empty case now states plainly that this is a DEFECT, that prose is not an available reply, where to look (trace back from Domain Box / Extrude / Cylinder / Boundary Surfaces to where the data stops), and that THIS measurement outranks any earlier turn.
- **The id-preservation root cause is now pinned and fixed** — see [[component-id-robustness]]. Short version: `Put` calls `NewSolution` internally, `CanvasStateGrounder` exports on every solve, that export calls `Resolve`, so all 48 fresh objects already held export-order ids before `RegisterStableIds` ran — and those interim ids overlap the authored ones, so claiming refused every time. `ClaimBatch` releases the batch's interim ids before claiming.

**Two things from that run I flagged before chasing them:**
- The Geometry Report said *"No geometry-producing components were found in the scanned scope"* — and the model dismissed it by citing an earlier geometry report that **never existed in that session** (feedback rounds were schema → required-input → runtime health → geometry report). It then declared the model complete. So either the report has a scope bug or the round-4 patch broke the graph, and either way the loop ended on fabricated evidence. Worth deciding whether a "nothing produced geometry" report should be allowed to terminate on a prose reply.
- `id claims verified: 1/48` again ([[component-id-robustness]]). Reproduction condition now clear: a canvas that already holds other components, which claim ids first.

**Fourth live run (23:46) — grouping correct, but components and group boxes OVERLAP.** Root cause is structural, not a prompt miss: **the model authors pivots but cannot know rendered sizes.** Grasshopper sizes a component from its nickname text and param count, so a slider we *require* to be nicknamed ("Main Block Width") renders 200+ wide into the 150-unit stage gap the prompt asked for, and a multi-line documentation Panel is ~130 tall, pushing each area's group box up into the area above. Measured from the authored doc: stages 150 apart in X; areas only **40** apart (Main Block y→160, Portico y→200) and **20** apart (Portico y→860, Wings y→880). The model also read "200+ gutter between areas" as horizontal-only, which the wording allowed.
- Fix (code, the reliable half): new `GhJsonBridge.Layout.cs` → `SeparatePlacedOverlaps(doc)`, called after full-document placement and after patch apply. Measures REAL bounds once, then nudges overlapping pairs apart in two levels with different clearances — components within a group (14) then whole groups as rigid bodies plus ungrouped strays (55, inflated by the ~10 margin GH draws a group box with). Deliberately NOT a relayout: each fix moves the LATER of a pair along the axis needing the smaller push, so column structure and reading order survive. Only model-placed objects move (authored-placement ledger); the user's own components are never touched.
- **Stale-bounds trap avoided:** level 2 must NOT re-read `Attributes.Bounds` after level 1 called `ExpireLayout()` — GH may not have recomputed. All geometry is measured once up front into `PlacedGeometry(pivot, offset, size)`, both levels run on rectangles derived from measurement + accumulated offset, and pivots are written exactly once at the end.
- Fix (prompt, the cheap half): pivots are mid-LEFT and the body grows right/down; real sizes stated (nicknamed slider 200+ wide, ordinary component 100-150, Panel ~150×130); stage gap 150→250, parallel 80→100, area gutter 200→250 **"in whichever axis they are adjacent"**, panel clearance 120→150; and an explicit note that Physalia measures and nudges, so prefer generous gaps over precision.
- Verified by replaying the real authored layout with estimated GH sizes: 10 component overlaps + Main Block↔Portico and Portico↔Wings box overlaps → **0 and none**, areas still in their authored arrangement (three stacked at x≈0, Dome right at x≈990). Stress-tested for termination: 40-on-one-point, dense 8×8 grid at 10px, 60 random, one giant + 30 small, already-clean — all reach 0 overlaps in ≤16 of the 24 allowed passes, and a clean layout is left untouched.

**Fifth iteration (2026-07-26) — nudging isn't enough; areas are now REBUILT from wires.** The separation pass removed overlaps but produced tall, wire-crossing areas instead of the wide column-per-stage shape a GH user expects. Two faults:
1. The axis rule picked the *smallest* overlap, so two components in the same row (small Y overlap, large X overlap) got pushed one below the other — cascading a row-aligned stage into a vertical stack. Now the axis follows the authored **topology**: compare centre offsets, so a pair placed side by side spreads sideways and a stacked pair spreads down.
2. More fundamentally, a nudge can only reach "not overlapping"; it cannot produce "one column per data-flow stage, sources left, terminal right". **Decision (user's, offered as a choice): per-area relayout from wires, gated on the area actually overlapping.** `RelayoutArea` — stage = longest wire path within the area, one column per stage sized to its widest member, members stacked down a column in the model's authored vertical order (row intent survives, coordinates don't), unwired members lifted above as captions, area keeps its top-left. **Terminals are forced to the last column** — longest-path staging alone seats the area's result ahead of a longer side chain (Domain Box two hops from a slider while Division→Negative→Construct Point runs three), which reads as the result being computed early. A cleanly authored area is still left exactly as-is.
- Verified on the real Main Block wiring: columns come out sliders / domains+division / negative / construct point / xy plane / **domain box last**, panel as caption, 0 overlaps, extent 1143×496 (aspect 2.30 vs the target screenshot's 2.72). Integrated over all four areas: per-area overlaps 1/4/2/3 → 0/0/0/0, no overlapping area boxes, 0 component overlaps anywhere.
- Note: the screenshots for this round came with the chat/trace files NOT re-exported (still the 23:46 pair), so the authored pivots for that specific run were never available — the diagnosis came from measuring the image (the three Construct Domains sat exactly `height + ComponentClearance` apart, proving the separation pass had stacked them).

**Sixth iteration (2026-07-26 00:26 session) — initial placement good, PATCH rounds wrecked it.** Two defects, from the chat:
1. **Full-document group ids were never claimed.** The library's `PutResult` reports only `GroupsCreated` (a count), no group id → guid map, so a full document's authored group ids were dropped and the next export renumbered every group (the model's 601-605 became 58…). The model then targeted `groups.modify {"match":{"id":602}}` by the number IT gave the group → `MatchNotFound at groups.modify`. That cost a round, and — because the failed modify was the ONLY thing tying that patch's two new components to an area — left them placed with no home. Fix: `RegisterPlacedGroupIds` recovers the pairing by **membership** (the live group whose ObjectIDs set-equal the placed guids of the authored group's members) and claims the ids. Verified: this document's five member sets are unique, so the match is unambiguous, and 601-605 don't collide with component ids 101-501.
2. **A `groups.modify` in a LATER patch changes membership but can never fix placement**, because positioning happens when a component is ADDED. The retry landed a round after the adds, so the components kept the position they got while homeless and the group box simply stretched to swallow them. Fix: `AreaIsFragmented` — single-linkage clustering over an area's members at a 400-unit gap; an area that is not spatially contiguous is rebuilt from its wires, not just nudged. Verified to discriminate correctly: a stray left right-of-graph → REBUILD, a stray already in a wire-inferred row just below its area → left alone.

**Layout is now logged.** Neither the chat export nor the signal trace records a pivot, so three consecutive layout regressions had to be diagnosed by measuring screenshots (the giveaway for one was Construct Domains sitting exactly `height + ComponentClearance` apart). `SeparatePlacedOverlaps` now writes a Rhino line: objects moved / total, largest shift, and how many areas were rebuilt with the reason (overlap vs fragmented). Read that first next time.

**Seventh iteration (2026-07-26 00:44 session) — patch adds must be INSERTED into the data flow, not parked below the area.** This run had zero failed operations and every `groups.modify` succeeded in the same patch as its adds, so homing worked exactly as designed — and the design was wrong. `PlaceWiredRowBelowGroup` parks group-homed wired adds in a row below the area, which is all a positioning pass can do at that point in the apply (the wires do not exist yet), but nothing ever moved them afterwards. Result: detached blocks of new components sitting inside the Roof and Portico boxes below the real graph. The user's framing was the fix: **existing components have to be pushed RIGHT to make room for a new node's column.**
- Fix: `SeparatePlacedOverlaps(doc, gainedMembers)` — the patch path passes `addedGuids`, and any area containing one is rebuilt from its wires **unconditionally** (not only on overlap/fragmentation). Inserting a node changes which column everything downstream belongs in, and only a rebuild shifts them. The full-graph path passes null, so a cleanly authored initial layout is still left untouched — the user explicitly likes that one. `PlaceWiredRowBelowGroup` is now documented as a STAGING position that survives only for an area with no usable wiring.
- Verified on the real Roof area (3 patches feeding it, adds 600/610/611/612/700): new components land in columns 0,1,2,3 interleaved with the originals, and **8 existing components move into later columns** to make room. No block below the area.
- Also confirmed working in this run: `RegisterPlacedGroupIds` from the previous iteration — group ids 501-504 survived into the canvas state, and there were no `MatchNotFound` failures.
