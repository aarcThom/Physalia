Standalone web chat window driving the GH pipeline, **additive** to the classic Prompter (both offered; classic keeps its canvas panel + Image Sources `/<alias>` input). Plugs into the [[signal-lifecycle]]. **Authoritative plan doc:** `planning/chat-window.md` in the repo.

## Shape
A `Chatbox` GH component (no inputs, one `Prompt Signal` output) owns a standalone Eto `WebView` window. Sending mints a Prompt Signal exactly like Prompter; the window reads the wired Recorder's conversation / live stream / busy state by **wire-graph traversal** (no inputs, so connecting a wire never re-solves) and pushes them to the page. Why small: Prompter was already signal-source + traversal-UI; the window reuses the traversal.

**Host = Eto.Forms `WebView`** (one class, WebView2 on Windows / WKWebView on Mac, uniform custom-URI bridge) — chosen for Mac-ease. Verified Windows engine = Chromium/WebView2 (`Edg/149`), so Svelte renders fine.

## The UI: `src/Physalia.UI` (new project in `src/Physalia.slnx`)
Vite + Svelte 5 + TS + Tailwind v4 + **shadcn-svelte** with **svelte-ai-elements** registry components (conversation, message, response, chain-of-thought, tool, prompt-input, image + shadcn bases), in `src/lib/components/{ui,ai-elements}`.
- **MSBuild wrapper** (compiles no C#): the Vite build runs only with `-p:BuildUI=true` or `npm run build` — a plain `dotnet build` needs no Node and uses the committed artifact.
- **Output:** `vite-plugin-singlefile` → one `index.html` → copied to **`Files/UI/chat.html`** (committed; rides the existing `CopyLibraryFiles` target into the `.gha` output). `ChatWindow` loads it via `file://` (path from `Assembly.Location`). singlefile = no module fetches, so `file://` works AND avoids the WebView2 `NavigateToString` ~2 MB limit.
- **Bundle 16 MB → ~3.4 MB:** streamdown-svelte (the Response markdown renderer) drags in Shiki-all-langs + mermaid(+cytoscape) + katex; singlefile inlines them all. `vite.config.ts` regex-aliases unused Shiki grammars (keep `json`), non-github themes, and `mermaid`/`katex` → empty stubs (`src/lib/shiki-empty-lang.ts` = `[]`; `src/lib/empty-module.ts` = noop Proxy). Safe — the chat enables no math/diagram plugins so those imports are never reached. `code/shiki.ts` trimmed to json+text, 2 themes.
- **Light mode forced:** NO `ModeWatcher` mounted, `.dark` never applied, `app.css` `color-scheme: light` (so response.svelte's `mode.current` → undefined → light theme).

## Required features (all implemented)
- **Thinking → ChainOfThought, tool calls → Tool.** Core conversation has NO reasoning channel, so `<think>…</think>` is parsed out of assistant text in the UI (`splitThinking` in `bridge.ts`) → ChainOfThought; the rest → Response. Tool calls are surfaced from `ToolCallContent` + the matching `ToolResultContent` (both in `MessageContent.cs`) → Tool component (state input-available / output-available / output-error). NB `ai-elements/tool/` has NO index.ts — import the `.svelte` files directly.
- **Images (reworked 2026-06-21):** the ai-elements `PromptInput` attachment intake was DEAD in the `file://` WebView — every path (picker/paste/drop) funnels into `AttachmentsContext.add()` which calls `crypto.randomUUID()` (throws, not a secure context) + `URL.createObjectURL` BEFORE storing, so the file was silently dropped (symptom: "Add image" opens the picker and nothing else happens). `Composer.svelte` was rewritten to do its own WebView-safe intake: `FileReader.readAsDataURL` → base64 (no blob URLs), counter ids (no `crypto.randomUUID`), plain DOM `paste`/`dragover`+`drop` (document-level, = old globalDrop)/hidden `<input type=file>`. Each add inserts a Claude-Code-style `[image#N]` token at the caret + a thumbnail in a strip above the textarea (× to remove → drops the token & renumbers). Tokens are composer-only: **stripped from the text before send** (regex `/\[image#\d+\]/g`); images travel as real `SubmitImage` blocks. Downstream UNCHANGED & already-correct: `App.svelte` `send()` (stash `__physaliaPending` + `phbridge://submit?images=1`), `ChatWindow.HandleSubmit`/`BuildMessages` (base64 ↔ `InlineImage`), conversation `<Image>` render. Builds + svelte-check clean; live Rhino test pending.
- **JSON auto-collapse:** LLM ghjson dumps flooded the chat. `bridge.ts` `splitContent(text)` splits an assistant body into prose vs JSON — catches ```json fences, unlabelled fences whose body parses as JSON, large bare JSON in prose (≥120 chars), and a large *unclosed* bare-JSON tail (collapses mid-stream). `AssistantTurn` renders prose via `Response`, each JSON segment via `chat/JsonBlock.svelte` (shadcn Collapsible, closed by default; the Code view + CopyButton mounts only when expanded, to skip Shiki cost). Non-JSON fences stay in prose.

## Bridge contract (`src/Physalia.UI/src/lib/bridge.ts` ↔ `Panels/ChatWindow.cs`)
- **C# → JS** via `ExecuteScriptAsync` on a 0.15 s `UITimer` (change-detected): `window.physalia.{setHistory(UiMessage[]), setStream(text|null), setState({connected,busy,ready,needsSetup,status})}`. (`ready` is pushed but the JS ignores it; `needsSetup` drives the setup screen — see below.)
- **JS → C#** via custom-URI navigation the host cancels:
  - text-only: rides the URL query `phbridge://submit?text=<enc>` (the proven path; `ChatWindow.GetQueryValue` parses it).
  - with images: sets `?images=1` and stashes the full JSON on `window.__physaliaPending` (base64 too big for a URL); host pulls it back via `__physaliaTake()` (with a one-layer JSON-unwrap in `ParseSubmitMessage`, since Eto may return the result JSON-encoded). **The pull MUST use `await _webView.ExecuteScriptAsync(...)`, NOT synchronous `ExecuteScript` — the sync variant on Eto/WebView2 pumps-and-waits and unreliably returns null, which silently dropped EVERY image send (text-only worked because it rides the URL). `HandleSubmit` is `async void` for this. Fix landed 2026-06-21 (.gha rebuilt), awaiting live confirmation; do not revert to sync ExecuteScript.**
- C# side: `OnDocumentLoading` sets `e.Cancel=true` synchronously, then **defers** the work via `Application.Instance.AsyncInvoke` (running a GH solve / ExecuteScript inside the nav callback re-enters the WebView core and crashes Rhino — same hazard as `ManageImagesDialog`'s grid-edit deferral). → `Chatbox.SubmitFromWindow(text, contentBlocks?)`.

## First-run setup state (landed 2026-06-21, builds clean)
Shown when **no LLM provider is configured at all** — distinct from the pipeline-wiring `ready` flag. Takes precedence over every other state (nothing to chat with until a provider exists).
- **Detection (C#):** `Panels/ProviderAvailability.AnyConfiguredAsync(apiKeyConfigPath, HttpClient, ct)` returns true if ANY of: an API key resolves from `API_KEY_CONFIG.YAML`/env (`Api.GetKeys(...).Count>0`), the Claude Code CLI is on PATH (`ClaudeCodeProvider.IsCliAvailable()` — new public method; delegates to `ClaudeCodeSession.IsCliAvailable()` → refactored `TryResolveExecutable(out path)`, a PATH-presence check, NOT auth), or a local llama-server answers `LlamaCppServerQuery.GetPropsAsync(new LlamaCppConfig(), ...)` at the default `http://127.0.0.1:8080/v1`. Cheap checks short-circuit before the network probe (the llama endpoint is only hit when nothing else is set up). "Claude detected" = **CLI installed on PATH** (user's explicit choice), not a running process.
- **Cadence:** `ChatWindow.MaybeProbeProviders()` runs the probe off the UI thread via `Task.Run` (3 s `CancellationTokenSource`; shared static `ProbeClient` with a 2 s `HttpClient.Timeout`), result published back on the UI thread (`Application.Instance.AsyncInvoke`). Cached in `bool? _providersConfigured` (null until first probe — assume configured so the setup screen never flashes), re-probed every 4 s so it clears within seconds of adding a key / starting a server. `Tick` reads the cache: `needsSetup = _providersConfigured == false`; when set, `status = "Setup mode"`.
- **UI:** `src/lib/chat/Setup.svelte` replaces the conversation surface when `showSetup` (in `App.svelte`, `{#if showSetup}<Setup/>{:else}…{/if}` inside `ConversationContent`). Placeholder red-smiley SVG (swap for real art later) + welcome + provider grid.

## Setup flow / provider guides (landed 2026-06-21)
Full interactive provider setup, driven by data + 3 new bridge verbs. The earlier "placeholder pages" note is superseded.
- **Provider data:** `src/lib/chat/providers.ts` — `PROVIDERS` array (claude-code, anthropic, google, openai, deepseek, local-llm, openrouter, other) each with `{needsKey, blurb, steps[], commands?[], links[], note?}`. `Setup.svelte` renders this uniformly: numbered steps, monospace command blocks, link buttons, and (for key providers) a "paste your key below" prompt. Guides written from live web research (current install cmds + canonical key-console URLs); `needsKey` true for anthropic/google/openai/deepseek/openrouter, false for claude-code/local-llm/other.
- **Live links open in the system browser:** the chat runs from `file://`, so an in-page `https` nav would replace it. Links call `onopenlink(url)` → `phbridge://open?url=<enc>` → `ChatWindow.HandleOpen` validates http/https and `Process.Start(UseShellExecute=true)`.
- **API key entry via the prompt box (not a Setup field):** when a `needsKey` provider's guide is open, `App` derives `keyProvider` and puts `Composer` in **API-key mode** (`apiKeyProvider` prop): box stays live even though setup disables it (`inert = busy || (disabled && !apiKeyProvider)`), image button hidden, submit calls `onsavekey(id,key)` instead of sending, and an `$effect` clears the box on any mode change so a typed key never leaks into a chat message. → `phbridge://savekey?provider=<id>&key=<enc>` (encodeURIComponent; no literal `+`, so `GetQueryValue` round-trips it).
- **Host save:** `ChatWindow.HandleSaveKey` maps the UI id → `(section, leaf)` (`KeyTargets`: anthropic→anthropic/api_key, google→gemini/api_key, openai|deepseek|openrouter→openai_compatible/<leaf> — matches `API_KEY_CONFIG.YAML.example`), `EnsureConfigFileExists` (copies the `.example` template, else `SetKey` writes a minimal file), then **`Physalia.Core.Config.Api.SetKey(path, section, leaf, value)`** (new) — line-based YAML editor that replaces/inserts `{section}.api_keys.{leaf}` preserving comments/other providers. Then resets `_providersConfigured=null` to force re-probe (key resolves on the next tick → setup clears), and pushes `window.physalia.setSetupResult({provider,ok,message})` (new host→JS verb; one-shot, not via Tick) which `Setup` shows as a green/red banner. **Key never logged.** NB the config file lives next to the assembly (bin/Files at dev time) so a `dotnet build` `RemoveDir` wipes it — same as the existing ApiKeys component; an installed `.gha` persists it.
- **Header dropdown to reopen setup:** `App` has a top `<header>` with a shadcn `DropdownMenu` (trigger = Menu+Chevron ghost button via `{#snippet child({props})}`); item "Set up providers…" sets `manualSetup=true`. `showSetup = needsSetup || manualSetup`; `canClose = !needsSetup` gates a "Back to chat" button (first-run can't close, manual can — so additional providers can be added anytime regardless of connection). `Set up providers…` works even mid-chat.
- Detection (`ProviderAvailability.AnyConfiguredAsync`) is back to real (the temp `return false` was reverted). Builds + svelte-check clean; live in-Rhino test pending.

## Bug fixes this session (all landed, build clean)
- **Send didn't work (Enter did nothing):** my first rewrite used the untested `ExecuteScript`-return "pull" for ALL sends; Eto's synchronous `ExecuteScript` return is unreliable. Fixed by routing text through the URL-query path. Also **stopped gating input on connection** (`Composer` `inert = busy` only; was `disconnected || busy`, which disabled the box with no Recorder wired). Disconnection is now just a placeholder hint.
- **Window froze while streaming/"thinking":** `Exec` used SYNCHRONOUS `ExecuteScript`, which blocks Rhino's UI thread; at ~7 Hz while streaming it froze the whole window. Fixed → `ExecuteScriptAsync` (fire-and-forget, `.ContinueWith` swallows faults), interval eased to 0.15 s.
- **Chat didn't scroll + composer scrolled away:** the stick-to-bottom scroll element is `ConversationContent` (had no `overflow-y-auto`/bounded height); `Conversation`'s hardcoded `h-full` fought the flex layout so the page overflowed. Fixed in `App.svelte`: `main` = `h-screen flex-col overflow-hidden`; wrap `<Conversation>` in `<div class="relative min-h-0 flex-1">`; `ConversationContent class="min-h-0 flex-1 overflow-y-auto"` (the scroll viewport); status + composer rows `shrink-0 border-t` so the composer stays pinned at the bottom.

## Gotchas
- **`chat.html` is now GITIGNORED (2026-06-21), NOT committed:** root `.gitignore` has `**/Files/UI/chat.html` (covers all three copies). It's a ~3 MB minified single-file bundle that was making the repo "90% HTML" — reproducible from `src/Physalia.UI`, so it's not tracked. Consequence: a fresh clone must build it (`npm run build` or `dotnet build -p:BuildUI=true`) or the window shows "UI not found". The files still must EXIST on disk in all three locations at runtime (see sync note below) — gitignore only stops them being committed. `Physalia.UI.csproj` comment updated to match.
- **Build now auto-refreshes `chat.html` into bin (2026-06-21):** `Physalia.GH.csproj` takes a build-ordering `ProjectReference` on `Physalia.UI` (`ReferenceOutputAssembly=false SkipGetTargetFrameworkProperties=true UndefineProperties="TargetFramework"` — the last two are REQUIRED, else GH's net7.0-windows TFM flows to the net7.0 UI wrapper and restore fails NETSDK1005). `BuildUI` now defaults **true** in `Physalia.UI.csproj`; the Vite target is incremental (`Inputs`=`src/**` + root config globs, `Outputs`=`Files/UI/chat.html`) so plain C# rebuilds skip npm. So a normal VS build (Ctrl+Shift+B / F5) or `dotnet build src\Physalia.GH` regenerates `Files/UI/chat.html` and `CopyLibraryFiles` stages it into `bin\<Config>\net7.0-windows\Files\UI`. Verified: clean Debug+Release land the html in bin; no-change rebuild skips Vite. Pass `-p:BuildUI=false` for a Node-free build. **Runtime still loads from next to the `.gha` (bin), so a C# change needs a Rhino restart; a UI-only change needs a rebuild + reopen the window.** VS caveat: editing only a `.svelte` file may leave GH "up to date" so VS skips the build — do Build/Rebuild to force it. Manual three-way copy is no longer needed.
- **Two tracked `Files` trees:** repo has BOTH root `/Files` AND `src/Physalia.GH/Files` — separate real dirs (not junctions), both git-tracked, identical content. GH `CopyLibraryFiles` reads root `..\..\Files` → bin → runtime resolves `Assembly dir/Files/UI/chat.html`. Keep `chat.html` synced in both (plus the bin copy above).
- **UI changes "didn't make it into the build" — two traps (hit 2026-06-22):** (1) **Per-config staleness** — `CopyLibraryFiles` stages `chat.html` into `bin\<Config>\…` only for the config you actually build, so building/iterating Debug leaves the **Release** bin frozen at whenever it was last built (a Release bin sat at the old red-smiley UI from days earlier while Debug was current). Build the SAME config Rhino loads (or build both). (2) **Manual `npm run build` + `cp dist/index.html → Files/UI/chat.html` poisons the incremental Vite check** — it makes the target's Output (`Files/UI/chat.html`) newer than all `src/**` Inputs, so the next `dotnet build -p:BuildUI=true` SKIPS the Vite rebuild (thinks UI is up to date). Harmless if the manual copy is current, but confusing. Reliable refresh of a given config's bin without fighting the incremental check: `dotnet build src\Physalia.GH -c <Config> -p:BuildUI=false` — Vite is skipped but `CopyLibraryFiles` still stages the current root `Files/UI/chat.html` into that bin (since it copies the whole `Files` tree on every build). Then restart Rhino (`.gha`/C# change) or just reopen the chat window (UI-only).
- **create-vite v9:** scaffold with exactly `--template svelte-ts --no-interactive --overwrite`; extra/unknown flags silently fall back to vanilla-ts.
- **shadcn-svelte add:** `use-clipboard` hook isn't shipped by the registry (had to hand-write `src/lib/hooks/use-clipboard.svelte.ts`); `code.svelte` `@reference`d the SvelteKit demo's `routes/layout.css` (repointed to `../../../../app.css`).
