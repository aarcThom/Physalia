Chat launcher **canvas widget** (`src/Physalia.GH/Widgets/ChatWidget.cs`, landed 2026-06-21). Renders the **Physalia jellyfish logo** (rasterized from `Images/logo.svg` → embedded `src/Physalia.GH/Resources/logo.png`, 215x256; picked up by the existing `Resources\*.png` embed glob — no csproj change), docked bottom-right of the GH canvas above the compass by default; **double-click opens** the standalone chat window (see [[chat-window.md]]). 2026-07-06: added the logo (replacing the old placeholder square) + **drag-to-move** (click-and-hold like the built-in GH widgets).

- Extends **`Grasshopper.GUI.Widgets.GH_Widget`** (NOT `GH_CanvasWidget_FixedObject` — uniform `Padding` can't stack above the compass independently, so we draw in device space ourselves).
- **Widgets are NOT auto-discovered** (unlike components). You MUST register via a `GH_AssemblyPriority` subclass whose `PriorityLoad()` does `GH_Canvas.WidgetListCreated += handler; return GH_LoadingInstruction.Proceed;` and the handler calls `e.AddWidget(new ChatWidget())` (`GH_CanvasWidgetListEventArgs`). Without this the widget never appears. `ChatWidgetPriority` lives in the same `ChatWidget.cs`. (Pattern confirmed from karamme/Parachute.) Once added, GH lists it in the canvas Widgets menu with a visibility checkbox automatically.
- `GH_CanvasMouseEvent` lives in namespace **`Grasshopper.GUI`** (not `.Canvas`). Widget Render runs UNDER the pan/zoom transform → must `g.ResetTransform()` and draw in device pixels (same as `SerializeWidget`); store the rendered `_frame` rect for `Contains`/`RespondToMouseDown` hit-testing.
- **Visible** is abstract on `GH_Widget`; backed by `Grasshopper.Instances.Settings.GetValue/SetValue("Physalia.ChatWidget.Visible", true)` so it defaults ON and the disable choice persists across sessions.
- **Mac / Windows compatibility: the whole widget file is wrapped in `#if WINDOWS`** (like `SerializeWidget`) — the widget API params are WinForms (`MouseButtons`, `ToolStripDropDownMenu`), `System.Drawing`/GDI is used for the logo render, and `UseWindowsForms` is Windows-TFM-only (`Physalia.GH` is `net7.0-windows` on Windows, `net7.0` on Mac). **Mac gets NO chat widget at all yet — Mac Todo.** Any widget change (logo, drag, etc.) is Windows-only until a Mac (Eto-based) path is built.
- **Interaction (2026-07-06 drag rework):** double-click → open; click-and-hold → drag to move. Mouse state machine across `RespondToMouseDown/Move/Up/DoubleClick`; a press only becomes a drag past a 4px threshold, gated on a `_pressed` flag only (NOT `e.Button` — a fast drag can report a non-Left button on move events).
  - **CRITICAL drag-capture gotcha:** returning `Handled` from `RespondToMouseDown` is NOT enough to become the active widget — without capture, GH only routes move events while the cursor is still over the icon (Contains-gated inactive path), so a fast drag that outruns the bounds drops mid-drag AND mouse-up may not arrive (leaving `_pressed` stuck → hover then drags). Fix: **explicitly `sender.ActiveWidget = this` on mouse-down** (public read/write `IGH_Widget` prop on `GH_Canvas`) and release it (`ActiveWidget = null` if it's us) on up/double-click. Then Move/Up route to us regardless of cursor position.
  - Position stored as **right/bottom edge offsets** (not absolute px) so it stays corner-anchored on window resize and clamps back on-screen; persisted via `Instances.Settings` (`Physalia.ChatWidget.RightOffset`/`BottomOffset`), same pattern as `Visible`, so it survives restart. Default = docked bottom-right above the compass.
- Open → `OpenChat`: find a `Chat` in `doc.Objects`; if none, `new Chat()` + `CreateAttributes()` (widget does NOT place it — the chat window drops it onto the canvas once a provider is available); then `chat.OpenWindow()` (reuses Chat's single-window static ownership). Widget is a launcher, not a pipeline participant.
- **Pipeline-wiring readiness**: `PromptPipelineView.IsPipelineReady(source, outputIndex)` = Chat→Conversation Log (output 0) AND Conversation Log output[1]→a `LLM Call` whose "Model" input has `SourceCount > 0`. `ChatWindow.Tick` pushes `ready` (+ a status naming the missing piece) in `setState`.
- **First-run setup state** (separate from `ready`, landed 2026-06-21): when NO provider is configured (no API key / no Claude CLI on PATH / no llama-server), `needsSetup` is pushed and the Svelte app shows `Setup.svelte` (provider-pick screen). Detection + interactive setup UI are now built — see [[chat-window]].
